# JWT con RS256

## En una frase

Un JWT es un pase firmado que dice "este es el usuario X, válido hasta tal hora"; con RS256, solo el servicio de autenticación puede firmarlo (clave privada) y cualquier otro servicio puede verificarlo (clave pública) sin consultar la base de datos.

-----

## Antes de empezar

Conviene que ya sepas:

* Cómo se verifica una contraseña: [Contraseñas con Argon2id](01-contrasenas-con-argon2id.md).

Palabras nuevas (también están en el [Glosario](Glosario.md)):

* **JWT (JSON Web Token):** Token con tres partes en Base64URL: header, payload y firma.
* **Claim:** Cada dato del payload, como `sub` (quién es) o `exp` (cuándo vence).
* **Firma digital:** Prueba matemática de que el contenido no se alteró y de quién lo emitió.
* **Firma simétrica (HS256):** La misma clave firma y verifica.
* **Firma asimétrica (RS256):** Una clave privada firma y una clave pública verifica.
* **Bearer token:** Token que da acceso a quien lo porte, sin más pruebas: como dinero en efectivo.

-----

## El problema: ¿quién eres en cada petición?

HTTP no tiene memoria. Después del login, cada petición tiene que demostrar de nuevo quién es el usuario.

Opción clásica: una **sesión** en el servidor (un ID aleatorio en una cookie que apunta a una fila en la base). Funciona, pero cada petición consulta la base, y si tienes varios servicios, todos necesitan acceso a esa tabla.

Opción con JWT: el token **lleva** los datos y una firma. El servicio lo verifica con matemática, sin consultar nada.

## La estructura

```
eyJhbGciOiJSUzI1NiIsImtpZCI6ImsyMDI2In0.eyJzdWIiOiJ1LTEyMyIsImV4cCI6MTc2MDI4MDAwMH0.Xk3...
└────────────── header ──────────────┘ └─────────────── payload ───────────────────┘ └ firma ┘
```

Decodificado:

```json
// header
{ "alg": "RS256", "kid": "k2026", "typ": "JWT" }

// payload
{
  "iss": "https://auth.tienda.com",
  "sub": "u-123",
  "aud": "api.tienda.com",
  "iat": 1760279100,
  "exp": 1760280000,
  "jti": "a1b2c3"
}
```

| Claim | Significa |
| --- | --- |
| `iss` (issuer) | Quién lo emitió |
| `sub` (subject) | De quién habla: el ID del usuario |
| `aud` (audience) | Para quién es: qué servicio debe aceptarlo |
| `exp` (expiration) | Cuándo vence |
| `iat` (issued at) | Cuándo se emitió |
| `jti` (JWT ID) | Identificador único del token |

**Firmado no es cifrado.** Cualquiera puede decodificar el payload con Base64 (prueba con jwt.io). Nunca pongas ahí datos sensibles: ni contraseñas, ni datos personales que no hagan falta.

## HS256 vs RS256

| | HS256 (simétrica) | RS256 (asimétrica) |
| --- | --- | --- |
| Claves | Un secreto compartido | Privada + pública |
| Quién puede firmar | Todos los que verifican | Solo el dueño de la privada |
| Si roban la clave de un servicio que verifica | Pueden fabricar tokens | No pueden: la pública solo verifica |

Con varios servicios, RS256 es lo correcto: el **servicio de autenticación** guarda la clave privada y firma; la **API** solo tiene la pública y verifica. Aunque comprometan la API, no pueden fabricar tokens.

```
           login OK
Usuario ─────────────> auth-service ── firma con clave PRIVADA ──> JWT
   │
   │  Authorization: Bearer <JWT>
   └──────────────────> API ── verifica con clave PÚBLICA ──> ¿válido?
```

## Emitir un token (servicio de autenticación)

Con la librería nimbus-jose-jwt:

```kotlin
fun emitirAccessToken(usuarioId: String, ahora: Instant): String {
  val claims = JWTClaimsSet.Builder()
    .issuer("https://auth.tienda.com")
    .subject(usuarioId)
    .audience("api.tienda.com")
    .issueTime(Date.from(ahora.toJavaInstant()))
    .expirationTime(Date.from((ahora + 15.minutes).toJavaInstant()))
    .jwtID(UUID.randomUUID().toString())
    .build()

  val header = JWSHeader.Builder(JWSAlgorithm.RS256).keyID(claveActual.keyID).build()

  return SignedJWT(header, claims)
    .apply { sign(RSASSASigner(claveActual)) }
    .serialize()
}
```

El access token dura **poco** (5 a 15 minutos). La razón está en la lección de [refresh tokens](04-refresh-tokens.md).

## Verificar un token (la API)

Validar la firma **no alcanza**. La lista completa:

1. **Algoritmo esperado.** Acepta solo `RS256`. Nunca uses el `alg` que dice el propio token: el ataque `alg: none` y la confusión RS256/HS256 vienen de confiar en él.
2. **Firma** con la clave pública correcta (elegida por `kid`, en la lección siguiente).
3. **`exp`**: no vencido, con un margen de unos segundos por diferencias de reloj.
4. **`iss`**: emitido por tu servicio de autenticación.
5. **`aud`**: emitido **para esta** API. Si no lo validas, un token de otro servicio tuyo sirve acá.

En Ktor, el plugin de autenticación JWT hace todo eso:

```kotlin
install(Authentication) {
  jwt("usuario") {
    realm = "api.tienda.com"
    verifier(jwkProvider, "https://auth.tienda.com") {
      withAudience("api.tienda.com")
      acceptLeeway(5)
    }
    validate { credencial ->
      if (credencial.payload.subject != null) JWTPrincipal(credencial.payload) else null
    }
  }
}
```

Y cada ruta declara cómo se autentica:

```kotlin
routing {
  authenticate("usuario") {
    get("/api/v1/pedidos") {
      val usuarioId = call.principal<JWTPrincipal>()!!.subject
      // ...
    }
  }
}
```

(Dentro de `authenticate`, el principal existe siempre; en código real conviene un helper que lo obtenga sin `!!` y responda `401` si falta.)

-----

## Resumen en 5 líneas

1. Un JWT tiene header, payload y firma; el payload se lee con Base64, así que no lleva secretos.
2. Los claims clave son `iss`, `sub`, `aud`, `exp`, `iat` y `jti`.
3. Con RS256, solo el servicio de autenticación firma con la clave privada; las APIs verifican con la pública.
4. Verificar es: algoritmo fijo, firma, `exp`, `iss` y `aud`. Nunca confíes en el `alg` del token.
5. Los access tokens duran minutos; en Ktor, `install(Authentication) { jwt { } }` y `authenticate { }` por ruta.
